# 多轮次建设目标

每轮都必须形成可运行、可测试、可演示的增量。下一轮开始前，上一轮必须满足其退出标准；若范围变化，先更新本文件和相关 ADR。

## 第 0 轮：设计基线（当前轮）

### 目标

- 明确产品范围、服务边界、领域模型和一致性策略。
- 固化工程约束、质量门禁和事实表达规则。
- 确定分轮交付顺序，避免一次性搭建空服务。

### 交付物

- `docs/00` 至 `docs/05`。
- `AGENTS.md`。
- ADR 模板与首批架构决策。

### 退出标准

- 文档之间无明显职责或状态语义冲突。
- 每个首版服务具有明确数据所有权。
- 第一条端到端业务链路和失败恢复方式可被完整说明。

## 第 1 轮：工程基线与分布式锁 Starter

### 目标

- 建立 Maven 多模块、统一依赖和本地启动方式。
- 按传统三层架构建立营销、积分、学习服务骨架。
- 基于 AOP + Redisson 实现注解式分布式锁 Starter。
- 通过工厂模式与策略模式支持可重入锁、公平锁、读锁、写锁，以及按顺序获取的双重锁。
- 建立统一响应、错误码、请求 ID 和异常处理。

### 验收场景

- 注解支持 SpEL 锁 Key、等待时间、租约、失败策略与锁类型。
- 双重锁第二把获取失败时第一把必定释放。
- 业务异常、超时和线程中断时只释放当前线程持有的锁。
- 全量单元测试通过，Starter 可被业务服务直接引用。

## 第 2 轮：知识付费拼团闭环

### 目标

- 引入 MySQL、Flyway、MyBatis-Plus 与版本化表结构。
- 使用责任链校验活动状态、活动时间、参与次数和拼团名额。
- 使用 Redis `INCR` 原子计数和 `SETNX` 自然业务键占位，失败路径执行可验证的名额回补。
- 在同一营销服务本地事务中更新交易订单、参与记录、团状态和通知任务。
- 异步发送成团/权益通知，并以失败重试和定时补偿保证最终一致性。

### 验收场景

- 100 个并发请求竞争 10 个名额，数据库确认人数不超过 10。
- 活动未开始、已结束、超过参与次数、重复请求和名额已满均正确拒绝。
- 数据库事务失败、订单重复和 Redis 短暂故障不造成永久多占或少占。
- 本地事务提交但即时通知失败时，通知任务可被重试/补偿并幂等发放权益。
- 迁移脚本可从空库执行，服务重启后订单与拼团状态不丢失。

## 第 3 轮：积分赛季排名

### 目标

- 使用 Redis Bitmap 记录每日签到状态并计算连续签到天数。
- 通过 RabbitMQ 异步发放积分，使用消息 ID 和积分流水唯一键保证幂等。
- 使用 Redis ZSet 构建实时赛季榜单，MySQL 保存积分事实流水。
- 积分明细按季度路由到物理分表，表名只能由受控季度计算生成。
- 使用 XXL-JOB 持久化榜单快照、补偿积分消息并归档历史赛季。

### 验收场景

- 同一天重复签到只计一次，跨月连续签到规则有自动化测试。
- 同一签到消息重复投递 10 次只生成一条积分流水。
- Redis 榜单丢失后可由季度积分流水重建。
- 赛季结算任务多实例触发不重复生成快照，失败后可安全重跑。

## 第 3.5 轮：OpenAPI 契约基线

### 目标

- 在 React 前端开发前为营销和积分服务提供机器可读契约。
- 统一描述操作、字段、错误响应、示例和 `X-Request-Id`。
- 使用自动化测试阻止接口文档与实际 Controller 漂移。

### 验收场景

- 两个服务的 `/v3/api-docs` 和 `/swagger-ui.html` 可访问。
- OpenAPI 包含当前全部外部路径、请求与响应 Schema；错误语义由统一 HTTP 规范描述，不在每个 Controller 重复堆叠注解。
- Testcontainers 环境中的契约测试通过。

## 第 3.6 轮：HTTP 接口基础设施

### 目标

- 统一 JSON 成功/错误响应、请求 ID 与字段校验错误。
- 按 HTTP 语义区分 400、404、409、405、415 与 500，禁止以 200 表示失败。
- 固化分页、幂等键、时间、ID、内部接口和异步事件契约规范。

### 验收场景

- 业务不存在返回 404，状态冲突和幂等键冲突返回 409。
- 错误响应使用统一 `Result<Void>`，包含稳定 `code`、`message`、`requestId` 和时间戳。
- 非法客户端请求 ID 被替换，合法请求 ID 在响应头和响应体中一致。

- 建立 IAM 服务、JWT 登录、网关认证和服务内资源鉴权。
- 为同步调用加入超时、熔断、隔离和有限重试。
- 完善健康检查、结构化日志、指标与链路追踪。

### 验收场景

- 可通过一次请求 ID 关联网关、交易、营销和权益日志。

### 5.8 小智 AI Agent（开发中）

- 新增独立 `knowledge-agent` 服务，使用 Java 17、Spring Boot 与 LangChain4j；服务拥有会话、消息、运行、工具审计、回答引用和消费幂等数据，不拥有课程、Note、进度、订单、积分或权益事实。
- 第一入口为全局右侧“问小智”，基于当前页面和用户有权访问的课程、进度与 Note 提供 SSE 流式、带来源回答。
- 第二入口为公开 Note 评论区 `@小智`，由 learning 在评论本地事务写 Outbox，经 RabbitMQ 异步触发；失败不影响原评论，重复事件不产生重复 AI 回复。
- 私人问答和公开评论使用不同工具白名单；服务端重新校验资源权限，公开回答不得读取私人数据。
- 首期不开放交易、权益、积分和发布内容等高风险写工具；仅在用户明确确认后考虑创建 Note 草稿。
- 公共资料向量存储确定采用 Qdrant，Embedding 采用百炼 `text-embedding-v4` 1024 维；语义切分、混合检索和重排仍需固定评估集验证，当前不得表述为已经实现。
- Agent 异步运行确定采用 MySQL 持久化状态机 + Agent 执行 Outbox + RabbitMQ Quorum 执行队列；运行通过数据库条件抢占、Lease 与 Fencing Token 防止多实例重复执行，生成与发布按检查点分别恢复。
- 初步方案见 `docs/19-xiaozhi-agent-initial-design.md`、ADR-0014 和 ADR-0015。
- 当前已完成独立 `knowledge-agent` 的无 RAG 流式问答原型、会话/消息持久化与历史界面、learning 评论 Outbox、消费幂等骨架及评论实际生成链路；评论运行已完成首版 Agent 执行 Outbox、Quorum 执行队列、手动 ACK、条件抢占、Lease/Fencing Token、`CONTEXT/GENERATE/PUBLISH` 检查点、默认 5 次上限的 10/60/300 秒 TTL 重试队列、租约续期与低频恢复任务。Agent 到 learning 已采用 IAM OAuth2 Client Credentials、RS256/JWKS、audience 与最小 scope 授权；用户会话 HS256 仍处于兼容迁移期。模型真实调用、发布失败恢复与死信重放尚未形成完整验收；RAG、来源引用、取消/断线恢复、模型 Memory、成本限制和网关端到端验收仍未完成。

## 第 6 轮：作品化交付

### 目标

- 建立 OpenAPI、架构图、演示数据和一键本地环境。
- 执行固定环境压测、故障演练和安全检查。
- 根据真实结果更新项目 README 与简历描述。

### 验收场景

- 新用户可完成登录、参团、支付、获得权益和学习课程的完整演示。
- 暂停、拖动、切换设备、离线重试和重复上报均不会破坏视频进度；Redis 清空后可由事实数据恢复。
- 核心链路有自动化回归脚本和可复现实验报告。
- README 中每项技术亮点都能定位到代码、测试或报告证据。

## 每轮工作节奏

1. **定义**：确认范围、场景、约束和验收用例。
2. **设计**：更新领域模型/API/数据/时序，必要时写 ADR。
3. **实现**：先领域测试，再适配器与接口，保持小步提交。
4. **验证**：运行单元、集成、端到端与非功能检查。
5. **复盘**：记录实际结果、遗留问题和下一轮入口条件。
