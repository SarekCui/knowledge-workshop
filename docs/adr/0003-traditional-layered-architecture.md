# ADR-0003：微服务内部采用传统分层架构

- 状态：已接受
- 日期：2026-09-03
- 决策人：项目维护者

## 背景

项目的首要目标是实现并验证简历中的拼团、积分赛季和分布式锁能力。原设计采用轻量 DDD 分层，但维护者明确要求所有业务服务使用传统架构，以降低概念和模块复杂度，使代码结构更符合常见 Spring Boot 项目习惯。

## 决策

所有服务统一采用 `controller -> service -> mapper` 三层主结构，并使用 `entity`、`dto`、`vo`、`config`、`mq`、`job`、`rule` 辅助包。

- Controller 负责 HTTP 协议、校验与响应转换。
- Service 负责业务编排、状态迁移和本地事务。
- Mapper 负责 MyBatis-Plus 数据访问。
- 拼团复杂校验使用 `rule` 包中的责任链，避免形成巨型 Service。
- 锁、幂等、消息等通用技术能力通过 Starter 或独立组件复用。

不创建 DDD 的 `domain/application/interfaces/infrastructure` 分层，不要求聚合根、领域仓储或端口适配器。

## 备选方案

- 轻量 DDD：业务表达力更强，但当前团队偏好和交付目标不匹配。
- 每个服务拆成多个 DDD Maven 模块：依赖边界更严格，但项目体量下样板代码和构建复杂度过高。
- 所有逻辑集中在 Service：初期快速，但会使事务、规则、缓存和远程调用难以测试，因此不采用。

## 影响

### 正面影响

- 目录直观，Spring 开发者容易理解和维护。
- 减少对象转换、接口抽象和 Maven 模块数量。
- 简历中的责任链、策略模式和本地事务可以直接定位到代码。

### 代价与风险

- Service 容易膨胀，必须通过规则链、状态服务和基础设施组件控制职责。
- Entity 容易越层泄漏，跨服务契约仍必须使用 DTO。
- 框架依赖更容易进入业务逻辑，测试需要明确隔离外部组件。

## 验证方式

使用 ArchUnit 或代码评审保证 Controller 不直接依赖 Mapper、服务之间不依赖实现模块，并为责任链、状态迁移和事务失败路径提供测试。
