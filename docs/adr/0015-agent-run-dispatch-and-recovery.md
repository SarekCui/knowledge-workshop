# ADR-0015：Agent 运行采用 MySQL 状态机与 RabbitMQ 执行队列

- 状态：已接受
- 日期：2026-09-18
- 决策人：项目维护者
- 关联决策：ADR-0014

## 背景

`knowledge-agent` 同时承载右侧私人问答和评论区 `@小智` 两类运行。当前评论原型由定时任务查询 `agent_run` 的 `PENDING` 记录，再更新为 `RUNNING` 后调用模型。该实现能验证链路，但在多实例下存在“多个实例先查到同一任务，再分别执行”的竞态；单纯依赖评论唯一索引只能避免重复业务结果，不能避免重复模型调用和费用。

模型调用还具有耗时长、结果不确定和外部副作用不可事务化的特点。数据库事务不能跨越模型调用或跨服务发布全过程，RabbitMQ 也只能提供至少一次投递，不能替代业务幂等、运行状态和崩溃恢复。

## 决策

- MySQL `agent_run` 是运行状态、执行检查点和恢复信息的事实源；RabbitMQ 只负责唤醒 Worker、削峰和多实例负载分配。
- learning 继续在评论事务内写 `AgentMentioned` Outbox。Agent 消费该事件时，在同一本地事务中写消费 Inbox、创建 `agent_run`，并写 Agent 自己的执行 Outbox；不得在 MQ 消费事务内直接调用模型。
- Agent 执行 Outbox 通过 Publisher Confirm 将 `ExecuteRun` 命令投递到独立执行队列。生产环境执行队列使用 RabbitMQ Quorum Queue、持久化消息、手动 ACK、有限 Prefetch 和 DLQ；本地环境允许单节点队列，但契约保持一致。
- Worker 收到执行消息后仍必须使用数据库条件更新抢占运行，不能把“收到消息”等同于“拥有任务”。抢占条件至少包含运行 ID、允许的来源状态和执行版本。
- `agent_run` 增加 `run_stage`、`lease_owner`、`lease_until`、`execution_version`、`next_retry_at`、阶段时间和错误分类。执行中按需要续租；租约过期的运行由恢复任务重新进入可执行状态。
- 所有阶段更新携带 `execution_version` 作为 Fencing Token。租约失效后的旧 Worker 不得覆盖新 Worker 的状态或结果。
- 运行生命周期状态为 `PENDING -> RUNNING -> SUCCEEDED`，可恢复失败进入 `RETRY_WAIT`，不可恢复或超过次数进入 `DEAD`；取消、超时分别进入 `CANCELLED`、`TIMED_OUT`。评论运行另外保存 `CONTEXT -> GENERATE -> PUBLISH` 阶段检查点，状态与阶段不得混为一个字段。
- 模型回答必须在 `GENERATE -> PUBLISH` 阶段迁移时先持久化，再调用 learning 发布回复。发布失败保留 `PUBLISH` 阶段，只能重试发布，不得重新生成回答。
- AI 回复使用 `agent:comment-reply:{sourceCommentId}` 作为业务幂等键，并由 learning 的来源评论唯一索引兜底。MQ 重复投递、消费者重启和发布响应丢失不得产生第二条 AI 回复。
- 错误按阶段和类型分类：上下文/网络/限流等可恢复错误采用有界指数退避；权限失败、资源下架和非法输入不重试；模型结果是否已经产生不明确时不得无预算地自动重新生成。
- RabbitMQ 4.1 使用 TTL 重试队列与 DLX 实现延迟重试；升级到支持内置延迟重试的版本前不得假设 Broker 已提供该能力。
- 保留低频 Reconciliation Job，恢复租约过期运行、重新投递长期未执行的 Outbox、继续发布已持久化回答并标记超过上限的死任务。
- 模型调用、Embedding、内部 HTTP 调用和回复发布必须位于数据库短事务之外。事务只负责抢占、检查点和状态条件更新。
- 首期不使用 Redis 分布式锁决定任务所有权，也不引入 Temporal。Redis 可用于限流、预算缓存和模型并发信号量；当出现长时间等待、人工审批、多 Agent 协作或复杂补偿流程时再评估持久化工作流引擎。

## 备选方案

- 仅用 MySQL 定时轮询：实现简单且可作为降级和恢复手段，但实时性、削峰和大规模 Worker 分发不如消息队列，不作为目标主链路。
- 只用 RabbitMQ 竞争消费者：无法记录完整运行状态，也不能消除 ACK 丢失、连接中断和外部副作用造成的重复执行，不采用。
- Redis 分布式锁：锁过期、续租和数据库状态一致性需要额外治理，且不能替代运行状态机、检查点和审计，不采用。
- Temporal 等工作流引擎：适合复杂持久化工作流，但会新增部署、运维和编程模型，当前两个场景收益不足，暂不采用。

## 影响

### 正面影响

- RabbitMQ 负责分发，MySQL 负责事实状态，职责清晰且支持水平扩容。
- 多实例重复领取不会导致多个有效执行者，旧执行者也不能覆盖新结果。
- 模型生成和评论发布分阶段恢复，可显著降低重复模型费用。
- 运行的每个阶段、重试、死信和恢复原因均可审计。
- 复用项目既有 MySQL、RabbitMQ、Outbox 和 Inbox 经验，不引入新的基础设施类型。

### 代价与风险

- Agent 需要新增执行 Outbox、运行阶段、租约、恢复 Job、重试队列和监控指标。
- 至少一次投递仍可能产生重复尝试；业务结果只能通过幂等和条件状态迁移达到 effectively-once，而不是宣称端到端 exactly-once。
- Quorum Queue、Publisher Confirm、手动 ACK、TTL/DLX 和 Prefetch 配置错误会影响可用性，需要集成测试和故障演练。
- 模型供应商通常不提供端到端幂等调用，执行租约只能降低重复生成概率，不能在所有网络故障下绝对消除重复计费。

## 验证方式

- 两个 Agent 实例并发消费同一运行时，只有一个实例能完成 `PENDING -> RUNNING` 抢占并调用模型。
- Worker 在抢占后、模型调用中、回答持久化后和回复发布后分别崩溃，运行均能从正确阶段恢复。
- 同一执行消息重复投递至少 10 次，只产生一条 AI 回复；已经持久化回答并进入 `PUBLISH` 阶段的运行不会再次调用模型。
- 租约过期并被新 Worker 接管后，旧 Worker 的状态更新因 Fencing Token 不匹配而失败。
- RabbitMQ 暂时不可用时，Agent 执行 Outbox 可恢复投递；超过重试上限的消息进入 DLQ 且运行状态可查询。
- learning 暂时不可用时只重试 `PUBLISH` 阶段；Note 变为非公开时运行终止且不泄露内容。
- 监控能够展示执行队列积压、活跃运行、租约过期、各阶段耗时、重试、死信、重复消息和模型调用次数。
