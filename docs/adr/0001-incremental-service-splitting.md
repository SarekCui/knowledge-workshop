# ADR-0001：按业务闭环渐进拆分微服务

- 状态：已接受
- 日期：2026-09-02
- 决策人：项目维护者

## 背景

目标系统最终包含课程、交易、营销、学习、积分和社区等能力。如果一开始创建所有服务，容易出现大量空模块、边界未经业务验证、开发环境复杂且无法形成端到端价值。

## 决策

首先围绕“拼团购买课程并获得权益”建立最小业务闭环。第 1 轮只实现工程基线、营销与交易的核心模型；持久化、消息、注册发现和其他领域按路线图逐轮加入。

服务拆分以独立业务能力和数据所有权为依据，不以技术组件或表数量为依据。

## 备选方案

- 一次性创建全部目标服务：目录完整，但空壳多且验证成本高。
- 先做完整单体再统一拆分：本地简单，但容易形成共享数据和模糊边界。
- 使用模块化单体长期运行：适合小团队，但不利于本项目演示跨服务一致性与治理目标。

## 影响

### 正面影响

- 每轮都有可运行结果和清晰验收证据。
- 业务边界可以在拆分前通过领域模型验证。
- 中间件复杂度与真实需求同步增长。

### 代价与风险

- 目标架构不能在第一轮全部呈现。
- 模块在后续轮次可能需要迁移或拆分。
- 必须持续维护契约和迁移文档，避免临时耦合固化。

## 验证方式

第 1 轮结束时，营销和交易领域测试应独立通过；第 3 轮结束时，完整交易闭环应能在服务重启和消息重复条件下最终收敛。
