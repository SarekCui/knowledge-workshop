# ADR-0004：前端开发前建立 OpenAPI 契约

- 状态：已接受
- 日期：2026-09-03
- 决策人：项目维护者

## 背景

项目即将使用 React 与 TypeScript 开发学员端和运营后台。若前端根据 Controller 或示例请求手写 DTO，字段、枚举、错误响应和接口路径容易发生漂移，也不利于 Agent 稳定生成代码。原路线图将 OpenAPI 放在作品化交付阶段，建立契约的时点过晚。

## 决策

- 将 OpenAPI 基线提前到前端工程创建之前，作为第 3.5 轮。
- Spring Boot 3.5 服务使用 Springdoc OpenAPI 2.x；当前锁定与 Boot 3.5.9 基线匹配的 2.8.15。
- 每个对外服务独立生成 `/v3/api-docs`，并在 `/swagger-ui.html` 提供调试界面。
- Controller 描述操作、状态码和业务错误；DTO/VO 描述字段、示例与枚举。
- 所有外部操作统一声明可选 `X-Request-Id` 请求头。
- 后续前端只从 OpenAPI 生成 API 类型与客户端，生成目录不得手工修改。

## 备选方案

- 前端手写 TypeScript 接口：启动快，但契约漂移风险高。
- 等第 6 轮再补 OpenAPI：无法在前端开发期提供机器可读契约。
- 使用 Springdoc 3.x：该主版本面向 Spring Boot 4，不符合当前 Boot 3.5 基线。

## 影响

### 正面影响

- 前端和 Agent 可以依据机器可读契约生成类型安全客户端。
- API 变更可以通过自动测试被发现。
- Swagger UI 提供可检索、可执行的接口说明。

### 代价与风险

- Controller 和 DTO 需要维护文档注解。
- OpenAPI 只能描述协议，业务状态迁移仍需设计文档补充。
- 多服务文档聚合与前端代码生成将在后续前端基线中完成。

## 验证方式

在 Testcontainers 集成环境启动营销和积分服务，请求 `/v3/api-docs`，断言服务元数据、路径、请求头、请求 Schema 及 200/400/500 响应存在；同时执行全模块单元测试与验收构建。
