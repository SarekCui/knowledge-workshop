# ADR-0007：使用 Nacos 服务发现与 Spring Cloud Gateway 动态路由

- 状态：已接受
- 日期：2026-09-07
- 决策人：项目维护者

## 背景

营销、积分和网关服务已经可以独立运行，但网关仍将目标地址写死为本机端口，无法支持服务实例扩缩容和故障实例摘除。项目已经采用 Spring Boot 3.5 与 Spring Cloud 2025.0，需要在同一技术体系内建立注册发现和客户端负载均衡。

## 决策

- 使用 Spring Cloud Alibaba 2025.0.0.0 和 Nacos 3.0.3 提供服务注册发现。
- 业务服务以 `spring.application.name` 注册，网关路由使用 `lb://{serviceId}`。
- 使用 Spring Cloud LoadBalancer 在网关侧选择实例，不引入 Dubbo 或 gRPC 第二套调用治理体系。
- Nacos 地址、命名空间和分组全部允许通过环境变量覆盖。
- 本地 Compose 使用无鉴权单机 Nacos，仅用于开发与演示；生产必须使用集群部署并开启认证。
- 网关在最前置全局过滤器中校验或生成 `X-Request-Id`，并向下游和响应透传。

## 备选方案

- 固定 URL：配置简单，但不支持多实例和自动摘除，拒绝作为目标形态。
- Dubbo 3：治理能力完整，但会与当前 Spring Cloud HTTP 体系形成重复能力，当前规模收益不足。
- Kubernetes Service：适合部署进入 Kubernetes 后使用，当前本地与作品化阶段暂不依赖集群平台。

## 影响

### 正面影响

- 网关不再感知服务实例的具体地址。
- 服务扩容后可由 LoadBalancer 自动分摊请求。
- 请求 ID 在进入网关时统一建立，便于后续日志与链路追踪。

### 代价与风险

- Nacos 成为新的运行依赖，必须配置健康检查、认证和生产高可用方案。
- 注册中心不可用时，已有实例缓存只能提供有限容错，不能替代注册中心高可用。
- WebFlux Filter 不得执行 JDBC、阻塞式 HTTP 等阻塞操作。

## 验证方式

- 单元测试验证合法请求 ID 透传及非法请求 ID 替换。
- 启动 Nacos、营销、积分和网关，确认服务注册并能通过 `lb://` 路由访问。
- 启动同名多实例并观察请求分布；停止一个实例后确认不再向其转发。
