# ADR-0002：视频进度采用可靠事件、MySQL 事实源与 Redis 投影

- 状态：已接受
- 日期：2026-09-02
- 决策人：项目维护者

## 背景

播放器会产生高频进度变化，业务同时需要低延迟断点读取、跨设备一致性、真实观看完成度和服务故障后的恢复能力。仅写 MySQL 会产生写放大；仅写 Redis 则可能在缓存故障时永久丢失学习记录。

## 决策

- 客户端按 15 秒节流，并在暂停、拖动、结束和退出时上报。
- 可靠 RabbitMQ 消息作为服务端高频写入缓冲，发布确认成功后才视为已接收。
- MySQL 保存进度事实快照和消费 Inbox，Redis 保存断点、会话、最近学习列表及观看 Bitmap 投影。
- 使用服务端 `sessionEpoch` 解决跨设备冲突，使用会话内 `sequence` 解决重复和乱序。
- 断点位置与真实观看完成度独立建模，拖动不直接计入观看区间。

## 备选方案

### 只写 MySQL，Redis Cache-Aside

实现简单且一致性直观，但即使客户端节流，高并发课程仍会产生大量小更新；后续行为分析也缺少自然的事件流。适合早期低流量版本，可作为降级实现。

### Redis Write-Behind 定时刷库

写入快，但 Redis 故障或刷库任务异常会丢失已向客户端确认的数据，且脏 Key 扫描与多实例协调复杂，因此不采用。

### 每次上报同时同步写 MySQL 和 Redis

没有跨资源原子性，接口延迟由较慢依赖决定，并且高频更新增加数据库压力。仍需处理一边成功一边失败，收益有限。

### 使用 Kafka 作为事件日志

吞吐、分区顺序与事件回放更适合超大规模，但项目既定技术栈使用 RabbitMQ，当前容量目标不需要额外引入 Kafka。若 RabbitMQ 队列积压和回放能力成为瓶颈，再以新 ADR 评估迁移。

## 影响

### 正面影响

- 写入可削峰，消息重复不会重复累计进度。
- Redis 丢失不会丢失已经确认的业务进度。
- 支持跨设备与离线迟到事件的确定性冲突处理。
- 观看事件可复用于课程聚合、学习分析和异常审计。

### 代价与风险

- 读取缓存与 MySQL 之间存在短暂最终一致窗口。
- 需要维护 publisher confirm、Inbox、条件更新、对账和缓存重建。
- RabbitMQ 不可用时客户端必须可靠保存并重试，交互逻辑更复杂。
- Bitmap 是近似投影，必须明确定义粒度和完成阈值。

## 验证方式

执行 `docs/06-video-progress-design.md` 第 12 节全部用例，并在固定环境记录上报吞吐、端到端持久化延迟、Redis 命中率、消息积压恢复时间和 Redis 清空后的重建结果。
