# ADR-0013：用户资料与头像对象存储

- 状态：已接受
- 日期：2026-09-16
- 决策人：项目维护者

## 背景

登录账号目前只有 IAM 内部用户名，社区页面直接显示用户 ID，无法管理公开昵称、头像和简介。头像二进制不适合写入 MySQL；笔记与评论又需要稳定、批量地获得作者公开资料。

## 决策

- `knowledge-iam` 拥有 `user_profile`，登录用户名继续属于账号身份，昵称、头像对象 Key 和简介属于用户资料。
- 用户本人通过 `/api/iam/profile` 查询和更新资料，使用 `version` 乐观锁防止多端覆盖。
- 社区通过有界批量接口 `/api/iam/users/public` 获取公开昵称和临时头像 URL，不逐条调用。
- 数据库只保存私有 Bucket 中的对象 Key；展示时生成临时签名 URL，不保存会过期的 URL。
- 前端提供方形裁剪弹窗，用户可拖动和缩放，自主决定头像显示范围，并导出256×256 JPEG。服务端只负责防御性魔数、大小、尺寸校验及重新编码；对已裁好的方形图片不会替用户重新选择范围。
- 首批头像只接受不超过 2MB、边长不超过 4096 像素的 JPEG/PNG。
- 上传新对象成功但资料更新失败时删除新对象；资料更新成功后尽力删除旧对象。后续可增加孤儿对象巡检任务。
- 跨服务基础设施抽取为 `knowledge-components/knowledge-object-storage` 普通底层依赖，统一提供对象写入、删除与临时签名读取；MinIO SDK 9.0.1 只存在于该模块。IAM 显式配置该能力并通过头像存储适配层使用，不向业务层泄漏厂商 API。待多个服务形成稳定、重复的配置模式后再评估 Starter，避免过早自动装配。
- 本地开发镜像按官方“社区版仅源码发行”的要求，从最后一个社区安全修复版本源码构建，且端口只绑定回环地址。该镜像只用于开发演示；生产环境必须使用持续维护的 S3 服务或具备有效许可且已修复当前安全公告的 MinIO AIStor，不能直接照搬本地 Compose。

## 备选方案

- 将图片写入 MySQL BLOB：增加数据库容量、备份和带宽压力，拒绝。
- 保存永久公开 URL：难以撤销，扩大隐私和缓存失效风险，拒绝。
- learning 服务逐条同步调用 IAM：造成 N+1 和强耦合，拒绝；首批由前端按当前页面作者批量读取。

## 影响

### 正面影响

- IAM 成为用户资料唯一事实源，社区不复制账号数据。
- 头像对象可独立扩容，接口对具体 S3 实现保持可迁移。
- 文件类型、尺寸和并发覆盖具有服务端约束。

### 代价与风险

- 临时 URL 会过期，长时间不刷新的页面需要重新查询公开资料。
- 数据库提交后删除旧对象失败会产生孤儿文件，需要后续巡检。
- MinIO 社区服务端已停止预编译发行，本地源码镜像不能作为生产方案。

## 验证方式

- IAM 集成测试覆盖查询、修改、过期版本冲突和公开资料批量查询。
- 单元测试覆盖图片魔数校验、居中裁剪和 256×256 重新编码。
- 前端测试覆盖资料状态、multipart 上传、批量作者资料缓存；真实浏览器验收个人中心和社区作者展示。
