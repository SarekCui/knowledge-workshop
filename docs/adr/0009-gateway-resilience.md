# ADR-0009：网关同步调用容错边界

- 状态：已接受
- 日期：2026-09-08
- 决策人：项目维护者

## 背景

当前真实同步调用发生在 Gateway 到 IAM、营销和积分服务之间。仓库尚无业务服务间同步 HTTP 调用，因此不能为了展示 OpenFeign 或容错组件虚构不必要的依赖链。网关调用下游时需要限制等待时间和并发故障扩散，并在短暂故障后自动恢复。

## 决策

- 使用 Spring Cloud Gateway 的 Netty HTTP Client 设置全局 1 秒连接超时和 3 秒响应超时。
- 使用 Spring Cloud CircuitBreaker + Resilience4j 为 IAM、营销、积分分别建立独立熔断器，防止一个服务的故障污染其他服务的统计窗口。
- 使用 Resilience4j `SemaphoreBulkhead` 实现按路由并发隔离，达到上限立即失败，不在线程池或无界队列中等待。
- HTTP 连接池使用固定上限，并限制连接获取等待时间。
- Gateway Retry 仅允许 GET 重试 1 次，使用 50—100 ms 退避；POST、PUT、PATCH、DELETE 等写请求不做透明重试。
- 超时、熔断打开、隔离拒绝和连接异常统一进入网关内部降级处理，返回 HTTP 503 与 `Result<Void>`，保留 `X-Request-Id`。
- 内部降级 URI 仅接受 CircuitBreaker forward；客户端直接访问时返回 404。

## 备选方案

- Sentinel：与 Nacos/Alibaba 生态结合紧密，但当前切片只需要本地可验证的熔断和隔离，引入控制台与规则推送会增加无关部署成本。
- 仅依赖 Netty 超时：能终止慢请求，但不能快速失败、隔离并发和验证故障恢复。
- 为业务服务增加 OpenFeign 调用：当前没有真实业务需求，会制造错误的服务耦合，因此暂不采用。

## 影响

### 正面影响

- 慢下游和故障下游有明确等待上限、并发上限和恢复状态机。
- 非幂等写请求不会因网关重试产生重复副作用。
- 每个服务独立熔断，可通过 Actuator/Micrometer 暴露 Resilience4j 与连接池指标。

### 代价与风险

- 网关配置增加，需要按容量测试调整并发阈值，当前数值不是生产容量承诺。
- 降级只表示基础设施暂时不可用，不返回伪造业务数据。
- 未来新增业务服务间同步调用时，仍需在调用方独立配置超时与容错，不能认为网关配置自动覆盖内部调用。

## 验证方式

- 故障下游首次 GET 返回 503、第二次正常时，网关只重试一次并返回成功。
- 同样的 POST 故障只到达下游一次。
- 下游响应超过 200 ms 测试阈值时，网关快速返回统一 503。
- 连续失败达到阈值后熔断器打开，不再访问下游；等待窗口后进入半开并在探测成功后关闭。
- 并发超过 Bulkhead 上限时立即抛出隔离拒绝，不等待许可证。
