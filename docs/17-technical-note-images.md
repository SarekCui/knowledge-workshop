# 技术 Note 图片设计

## 1. 范围与原则

- 图片作为 Note 正文资源，不建立重复文章或附件领域。
- 前端上传 JPEG/PNG 后，Markdown 只保存 `/api/learning/note-images/{imageId}` 稳定标识，禁止保存 MinIO 临时签名地址。
- 图片对象存储复用 `knowledge-object-storage`，学习服务负责图片归属、引用关系、访问授权和清理生命周期。
- 首批每张原图最多 5MB、最长边不超过 8192 像素、总像素不超过 2400 万；每篇 Note 最多引用 20 张站内图片。

## 2. 写入与事务

1. 上传接口校验声明类型和二进制签名，只接受 JPEG/PNG。
2. 服务端解码并将最长边压缩到 1600 像素以内，重新编码以剥离元数据，再写入 MinIO 私有 Bucket。
3. 数据库创建 `TEMP` 图片记录，归属当前用户，24 小时内未被使用可清理；每个用户最多保留 20 张临时图片。
4. 创建或更新 Note 时解析正文中的稳定图片 ID，在同一个本地事务内校验所有权并转为 `BOUND`。
5. 正文移除图片或删除 Note 时，图片重新转为 `TEMP` 并进入 24 小时回收窗口；数据库事务回滚时绑定变化一起回滚。

上传对象成功但数据库写入失败时立即尝试删除对象。对象存储和 MySQL 之间不伪装分布式事务，残留对象通过受控对象 Key 前缀和后续存储巡检处理。

## 3. 读取与授权

- 图片 Bucket 保持私有，不向前端暴露永久公开 URL。
- 作者可以读取自己的 `TEMP` 或 `BOUND` 图片；其他用户仅能读取已绑定到公开且未删除 Note 的图片。
- 授权接口返回 1 小时有效的 MinIO 签名地址；Markdown 渲染组件先携带登录态请求授权，再加载图片。
- 外部 Markdown 图片不渲染，避免第三方追踪像素和绕开内容归属治理；原始 HTML 继续由 Markdown 安全策略禁止。

## 4. 清理与并发

`note_image` 使用 `TEMP / BOUND / DELETING` 三态。定时任务先以唯一 `cleanup_token` 批量认领到期记录，再删除对象：

- 对象删除成功后按 `id + cleanup_token + DELETING` 条件删除数据库记录；
- 删除失败恢复为 `TEMP`，一小时后重试；
- 超过十分钟仍处于 `DELETING` 的记录视为中断认领并恢复；
- 保存 Note 与清理竞争时，条件更新和状态校验阻止已认领对象重新绑定，客户端得到冲突后刷新重试。

## 5. 前端边界

- 上传动作、忙碌态和错误由 `NoteStore` 经 `NoteContext` 提供，不通过多层组件参数传递。
- 工具栏组件只负责选择文件和按当前光标位置插入 Markdown；不自行持有业务请求状态。
- 图片组件在卸载后忽略在途授权响应，使用懒加载与异步解码，并为加载和失败状态提供可访问文本。
- 本批不包含图片库、拖拽排序、富文本所见即所得、CDN 图片处理或内容审核。
